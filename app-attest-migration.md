# App Attest migration — replacing `APP_TOKEN`

**Status:** draft / not started
**Author:** drafted 2026-09-03
**Supersedes:** the `APP_TOKEN` ↔ `APP_SHARED_TOKEN` shared-secret gate

---

## 1. Why

`APP_TOKEN` cannot be made secure. It ships inside the IPA, so anyone can unzip
the bundle and read it out of the Expo manifest. Rotating it more carefully does
not change that — the value is only ever a speed bump, and it is one that any
motivated person steps over in about ten minutes.

App Attest replaces "the caller knows a secret that is printed inside the app"
with "the caller can prove, cryptographically, that it is a genuine copy of our
app running on a real Apple device." The proof is generated by a key held in the
Secure Enclave, so there is nothing embedded in the binary to extract.

**What it fixes**

- Strangers calling `/api/analyze` directly and billing our Anthropic account.
- Scripted/bulk abuse from non-app clients.
- The scan quota being fiction. Today the 5/day cap lives in the app's own
  `AsyncStorage` (`apps/mobile/lib/utils/scanQuota.ts`) and resets on reinstall.
  An attested `keyId` is a trustworthy per-device identity, so the cap can
  finally be enforced **server-side**. This is arguably the bigger win.

**What it does NOT fix**

- A legitimate user of the real app making expensive-but-allowed requests.
  That is what the rate limiter and the Anthropic spend cap are for.
- Anything on Android (see §9).
- Jailbroken devices, in the general case.

App Attest is a gate on *who may call the API*. It is not a spend cap. Keep the
durable rate limiter and the Anthropic spend cap underneath it, permanently.

## 2. How App Attest works

Two phases. Apple's `DCAppAttestService` (iOS 14+, **physical devices only**).

**Attestation — once per install**

1. Client calls `generateKey()` → a `keyId`. The private key lives in the Secure
   Enclave and is never extractable.
2. Client asks our server for a one-time **challenge** (random nonce).
3. Client calls `attestKey(keyId, clientDataHash: SHA256(challenge))` → a CBOR
   attestation object.
4. Server verifies it (the fiddly part):
   - Parse CBOR; expect `fmt = "apple-appattest"`.
   - Verify the `x5c` certificate chain up to the **Apple App Attest Root CA**.
   - Recompute `nonce = SHA256(authData ‖ SHA256(challenge))` and check it
     matches the credCert extension OID `1.2.840.113635.100.8.2`.
   - Check `keyId == SHA256(publicKey)`.
   - Check the first 32 bytes of `authData` equal `SHA256("<TeamID>.<BundleID>")`
     → `SHA256("YR4B6LSC95.com.eatoutbetter.app")`.
   - Check the counter is `0` and the `aaguid` is `appattestdevelop` (dev builds)
     or `appattest\0\0\0\0\0\0\0` (production).
5. Server stores `keyId → { publicKey, counter: 0 }`.

**Assertion — proving a later request came from that same key**

1. Server issues a challenge.
2. Client calls `generateAssertion(keyId, clientDataHash: SHA256(clientData))`.
3. Server verifies the signature against the stored public key and checks the
   counter has **strictly increased** (replay protection).

> ⚠️ Do not hand-roll the CBOR/X.509 verification. A subtly wrong implementation
> that accepts forged attestations is worse than no attestation at all, because
> it buys false confidence. Use a maintained library (`node-app-attest`, or
> `@peculiar/x509` + `cbor-x`) and write tests against Apple's sample vectors.

## 3. Target architecture

Asserting on **every** `/api/analyze` call would add a challenge round-trip plus
Secure Enclave crypto to every scan — meaningful latency on the exact action the
product is built around. Instead, exchange one attestation for a short-lived
token:

```
  ┌── first launch ──────────────────────────────────────────────┐
  │  app                          api                            │
  │   │  GET  /api/attest/challenge  ──────────►                 │
  │   │  ◄──────────────────────────  { challenge, ttl: 5m }     │
  │   │  attestKey(keyId, SHA256(challenge))                     │
  │   │  POST /api/attest/verify  ─────────────►                 │
  │   │        { keyId, attestation }            verify + store  │
  │   │  ◄──────────────────────────  { deviceToken, exp: 24h }  │
  └───┴──────────────────────────────────────────────────────────┘

  ┌── every scan ────────────────────────────────────────────────┐
  │   POST /api/analyze                                          │
  │   Authorization: Bearer <deviceToken>       ← replaces        │
  │                                               x-app-token     │
  └──────────────────────────────────────────────────────────────┘
```

`deviceToken` is a server-signed JWT carrying `{ keyId, exp }`, signed with a
new `DEVICE_TOKEN_SECRET` (server-only, never shipped). On expiry the client
silently re-attests — or, cheaper, refreshes with an **assertion** rather than a
full attestation.

Why this shape:

- One attestation per install, not per request. Latency stays where it is.
- `keyId` inside the token is the durable device identity the server-side scan
  quota needs.
- Slots into the existing header-check seam in
  `apps/api/src/app/api/analyze/route.ts` (`isAuthorized`), so the blast radius
  on the analyze route is small.

## 4. Server work

| Component | Notes |
|---|---|
| `POST /api/attest/challenge` | Random 32-byte nonce → Redis, 5-min TTL, single-use. |
| `POST /api/attest/verify` | Full attestation verification (§2). Issues `deviceToken`. |
| `POST /api/attest/refresh` | Assertion-based token refresh; bumps stored counter. |
| `lib/attest/verify.ts` | Verification logic. Library-backed, unit-tested. |
| `isAuthorized()` rewrite | Bearer JWT verify, replacing the `x-app-token` compare. |
| Storage | Challenges + counters → Upstash Redis (already provisioned for rate limiting). `keyId → publicKey` wants real durability → Supabase, when V1 lands. |
| Env | `APPLE_TEAM_ID`, `APP_BUNDLE_ID`, `DEVICE_TOKEN_SECRET`, `ATTEST_ENFORCEMENT` (see §6). |

## 5. Client work

`DCAppAttestService` is native — there is no pure-JS path.

- Use a community Expo module (e.g. `expo-app-attest`) or write a small custom
  native module + config plugin.
- **This is a native change.** It cannot ship via `eas update`; it needs a new
  TestFlight/App Store build. Per the `runtimeVersion: { policy: "appVersion" }`
  fence documented in `apps/mobile/app.config.ts`, **bump `version`** so OTA
  payloads can't reach binaries lacking the native module.
- Store `keyId` and `deviceToken` in `expo-secure-store`, not `AsyncStorage`.
- `isSupported === false` on the Simulator, so the dev path must be able to skip
  attestation locally (see §6).

## 6. Rollout — the part that breaks things if rushed

This has exactly the failure mode already identified for `APP_SHARED_TOKEN`:
turning the gate on 401s every installed build that cannot satisfy it, including
public App Store builds. Ship behind an `ATTEST_ENFORCEMENT` env var with three
states, changeable in Vercel without a deploy:

**Phase A — `off`** *(ship here)*
Attestation endpoints live; `/api/analyze` ignores attestation entirely.
Client attests in the background and attaches `deviceToken` when it has one.
Server logs which path each request used. Zero user-visible risk.

**Phase B — `monitor`**
Server verifies tokens when present, still serves requests without them, and
records the attested share. Wait here until the attested share plateaus and
older builds have drained. **This is the gate on Phase C — do not time-box it.**

**Phase C — `enforce`**
Unattested requests are rejected. Return a distinct, actionable error
(`UPDATE_REQUIRED`) rather than a bare 401, so the app can show "please update"
instead of a generic failure.

Roll back by setting the env var to `monitor`. No deploy, no build.

## 7. Failure policy

App Attest fails for reasons that are not abuse: no network, Apple's attestation
service down or rate-limiting us, Simulator, some enterprise/managed devices.
A hard failure here bricks the core feature, so:

- **Attestation fails →** fall back to a degraded anonymous tier (tighter rate
  limit, lower daily cap), not a hard block. Log it.
- **Apple service unavailable →** fail open to the degraded tier, and alert.
- **Counter regression / bad signature →** hard reject. That is genuine replay.
- **Simulator / dev →** `ATTEST_ENFORCEMENT=off` locally; never bypass on a
  value the client controls.

The guiding rule matches the rest of this codebase: cost guards fail open,
integrity checks fail closed.

---

## 8. Server-side scan quota (the payoff)

Once `keyId` is trustworthy, move the daily cap server-side:

```
eob:quota:<utc-day>:<keyId>  → INCR, TTL 25h, cap at DAILY_SCAN_LIMIT
```

Keep the client-side check in `scanQuota.ts` as a UX affordance — it avoids
uploading photos that are going to be refused — but stop treating it as the
control. Reinstalling the app no longer resets the allowance, because the
Secure Enclave key survives it.

---

## 9. Android

`app.config.ts` already declares `com.eatoutbetter.app` for Android. The
equivalent is the **Play Integrity API**, same shape (challenge → verdict →
server verification) but a different verification path and a Google Cloud
project dependency. Design the server so `verifyDeviceProof()` dispatches on
platform; do not let App Attest details leak into the analyze route.

## 10. Effort and risk

| | |
|---|---|
| **Effort** | ~2–4 focused days: 1 native/client, 1–2 server verification + tests, 0.5 rollout plumbing. |
| **Cost** | App Attest is free. Verification is cheap CPU. |
| **Main risk** | Getting verification subtly wrong. Mitigate with a real library + Apple's test vectors. |
| **Second risk** | Enforcing too early and 401ing live users. Mitigate with §6. |
| **Dependency** | Needs a new native build; cannot go out over OTA. |

---

## 11. Decisions needed before starting

1. **Is this worth it yet?** Attestation matters once the endpoint is genuinely
   worth attacking. If the durable rate limiter plus the Anthropic spend cap
   already bound the downside to an acceptable number, this can reasonably wait
   until after the App Store launch.
2. **Community module or custom native module?** Custom is more work but removes
   a dependency on an unmaintained package in the auth path.
3. **Does `keyId` storage wait for Supabase**, or go into Redis now and migrate?
4. **What is the degraded-tier quota** for devices that legitimately cannot
   attest?

---

## 12. Interim position

Until this ships, the honest posture is:

- `APP_TOKEN` is a speed bump. Rotate it **once**, cleanly, and stop spending
  attention on it.
- The real protections are the durable rate limiter (`lib/utils/rateLimit.ts`,
  including the global daily circuit breaker) and the Anthropic spend cap.
- Do not enable `APP_SHARED_TOKEN` until v1.1.4+ is widely adopted — and when
  you do, understand you are buying a speed bump, not a gate.
